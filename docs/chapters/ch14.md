# Chapter 14: Deploying to Azure

Tag: `ch14` · Compare: `git diff ch13 ch14` (until earlier chapter tags exist, compare with `main`)

## What PriorAuthBot has now

A production deployment on Azure with no long-lived secrets, no public endpoints for data, and a release pipeline that ships a commit only after its gates pass and a canary holds.

- **The infrastructure as Bicep** (`infra/`): an internal Container Apps environment in a VNet, Azure OpenAI with pinned model versions, PostgreSQL Flexible Server with pgvector, a Blob container with an immutability policy for the audit archive, Key Vault, Log Analytics and Application Insights, optional Azure AI Search, and alert rules. `azd up` or the deploy workflow applies it.
- **Managed identity everywhere.** Three user-assigned identities: the API, the migration job, and the eval job. Azure OpenAI, AI Search, Storage, Log Analytics, and Application Insights have local (key) auth disabled; PostgreSQL has password auth disabled. The API signs in to PostgreSQL with an Entra token that Npgsql refreshes (`PostgresDataSource`). There is no connection string with a secret in it anywhere.
- **Private networking.** Every data service has `publicNetworkAccess: Disabled` and a private endpoint. The API has internal ingress only. The container registry is public but Entra-only (images hold no data), and telemetry goes to the public ingestion endpoints with Entra auth.
- **Least-privilege database access.** The API's role can insert into the audit table and read it, read and write the ledger and the vectors, and nothing else: no `CREATE`, `ALTER`, or `DROP`. A separate job, `PriorAuthBot.Api migrate`, runs as the database administrator before each release.
- **Entra sign-in with app roles.** `infra/entra/app-registration.bicep` (the Microsoft Graph Bicep extension) registers the API with the `PriorAuthBot.User` and `PriorAuthBot.AuditReader` roles, assigns them to groups, and requires an assignment. The API rejects a valid token without `PriorAuthBot.User` (403).
- **A shared token ledger.** `Usage:Ledger=Postgres` keeps budgets right across replicas. (Chapter 13 suggested Redis; one PostgreSQL table we already run turned out simpler and fast enough. See the chapter.)
- **The audit archive.** Every 15 minutes, a background service checks the chain and copies new records and an anchor (last sequence and hash) to write-once blobs. A broken chain is a critical log event (1311) and an alert.
- **Production startup checks.** `ProductionReadiness` lists every problem at once and the API refuses to start: in-memory stores, Entra sign-in or the required role missing, a managed identity missing when an Azure service is configured, placeholder values, or a secret in a settings file.
- **Health probes.** `/health/live` (the process) and `/health/ready` (ingestion done, PostgreSQL reachable) for Container Apps' startup, liveness, and readiness probes. Both report the revision.
- **The release pipeline** (`.github/workflows/deploy.yml`): CI gates on the commit, image build, Trivy scan, SBOM, provenance attestation, then in the `production` environment: OIDC sign-in, Bicep, image push, migration, a new revision with no traffic, a smoke test and the eval and red-team gates against it from inside the VNet, 10 percent of traffic for 15 minutes, a failure-rate comparison, and promotion. Any failure sends all traffic back to the stable revision. `rollback.yml` does the same by hand.

## Running it

Locally nothing changes: `dotnet run --project src/PriorAuthBot.AppHost` or the API alone, as in chapter 13. Two things are new to try without Azure:

```bash
# The image as it runs in production (the CI "Container image" job does this):
docker build -f src/PriorAuthBot.Api/Dockerfile --build-arg REVISION=local -t priorauthbot-api .

# The startup checks: Production with the Development settings refuses to start and lists why.
ASPNETCORE_ENVIRONMENT=Production dotnet run --project src/PriorAuthBot.Api

# The smoke test against any running instance:
dotnet run --project eval/PriorAuthBot.Eval -- --smoke http://localhost:5080/ --wait 60
```

### Deploying

You need an Azure subscription with Azure OpenAI access, and permission to create app registrations.

1. Register the API in Entra ID: `az deployment group create -g <rg> -f infra/entra/app-registration.bicep -p groupIds='[...]'`. Note the `appId` output.
2. Either `azd up` (sign-in as you), or the pipeline: run `infra/bootstrap/github-oidc.sh <owner/repo> <env-name> <location>`, set the repository variables it prints plus `PRIORAUTHBOT_API_CLIENT_ID`, and create two GitHub environments: `production` with required reviewers, and `production-override` with the security lead as its only reviewer. The Azure identity trusts only the `production` environment's OIDC subject.
3. Push to `main`. When CI passes, the deploy workflow waits for approval, then releases.

**After the first deployment, lock the audit archive's immutability policy.** A locked policy can be extended but never shortened or removed, by anyone, including the subscription owner. Locking cannot be undone, which is why the template leaves it unlocked:

```bash
etag=$(az storage container immutability-policy show -g <rg> --account-name <AUDIT_STORAGE_ACCOUNT> -c audit-archive --query etag -o tsv)
az storage container immutability-policy lock -g <rg> --account-name <AUDIT_STORAGE_ACCOUNT> -c audit-archive --if-match "$etag"
```

**A secret you cannot avoid** (a third-party API key) goes in Key Vault, never in settings or the template. Add it to the container app as a Key Vault reference, read with the API's identity, and point a setting at it:

```bash
az containerapp secret set -g <rg> -n <app> --secrets "vendor-key=keyvaultref:https://<vault>.vault.azure.net/secrets/vendor-key,identityref:<api identity resource ID>"
az containerapp update -g <rg> -n <app> --set-env-vars "Vendor__ApiKey=secretref:vendor-key"
```

### Changing the model

Model versions are pinned: each Azure OpenAI deployment has `versionUpgradeOption: NoAutoUpgrade`, and its name carries the version (`gpt-4-1-mini-2025-04-14`). To roll out a new one, add it to `chatDeployments` in `main.bicep`, set `chatDeployment` in `infra/release.json` to its name, and push. The new revision uses it, the eval and red-team gates run against it before any user sees it, and the canary compares it with the stable revision. Rolling back the revision rolls back the model, because each revision names the deployment it was tested with.

### Rolling back

Actions > Roll back > Run workflow, with a reason. Empty revision means the one before the current. It takes about a minute: the earlier revision is still deployed.

## Configuration

| Setting | Meaning |
|---|---|
| `Azure:ManagedIdentityClientId`, `Azure:TenantId` | The user-assigned identity for every Azure call; required in production when any Azure service is configured |
| `Postgres:Authentication` | `Password` (default, local) or `Entra` (Azure: no password allowed in the connection string) |
| `Postgres:TokenRefresh` | How often the Entra token is refreshed (default 30 minutes) |
| `Auth:RequiredRole` | The app role every user needs (default `PriorAuthBot.User`) |
| `Usage:Ledger`, `Usage:CreateSchema` | `InMemory` (default) or `Postgres` (required in production with quotas on) |
| `Audit:Archive:Provider`, `ContainerUri`, `Interval`, `MaxRecordsPerBatch` | `None` or `Blob`; the container; every 15 minutes; 5,000 records |
| `Telemetry:AzureMonitor:ConnectionString` | Application Insights (or `APPLICATIONINSIGHTS_CONNECTION_STRING`); Entra auth, no key |
| `PriorAuthBot:Revision` | Reported by the health probes; set from the commit in the image |
| `Migrate:AppRole`, `Migrate:AppPrincipalId` | The API identity's PostgreSQL role, for `migrate` |

## CI

| Job | What it adds in this chapter |
|---|---|
| Build and test | Startup checks, health probes, role requirement, archive, Bicep and workflow policy tests |
| Integration (pgvector) | 60 concurrent charges across three ledger replicas; the API role's privileges after migration; the smoke test against the API configured as in Azure |
| Secret scan | gitleaks over the whole history |
| Dependency review | Pull requests that add a vulnerable or GPL package fail |
| Infrastructure | `az bicep build` and the linter, with warnings as errors |
| Container image | Both images built, scanned with Trivy, an SBOM with syft, then the API image run in Production against pgvector and smoke tested |
| Model canary | The eval and red-team gates on a weaker candidate model (`llama3.2:1b`), to show the gate refusing it |

The deploy workflow requires the build, pgvector, RAG eval, secret scan, container image, and infrastructure jobs to have passed on the commit. An override needs the `production-override` environment's approval and a written reason.
