## What PriorAuthBot has now

Tools. `POST /assist` gives the model three tools of PriorAuthBot's own (look up a policy by number, check your own PTO balance, open a help desk ticket) and the vetted tools of an MCP server that ships in the repo (the drug formulary). `FunctionInvokingChatClient` runs the read-only tools; the ticket, a write, comes back as a pending action that runs only when the same user approves it, with the arguments they saw. The PTO tool calls a mock HR API with an on-behalf-of token for the user; PriorAuthBot has no access of its own. PriorAuthBot's permission-aware search is also published as an MCP server at `/mcp`, behind the same sign-in.

## Running it

```bash
dotnet build MasteringAI.slnx                                  # builds the formulary server the API starts
dotnet run --project samples/mock-apis/DeductibleDynamics.MockHr   # http://localhost:5180
dotnet run --project src/PriorAuthBot.Api                          # http://localhost:5080, or use the AppHost
```

Then open `http://localhost:5080/ui`, choose **Use tools**, and ask "How much PTO do I have left?" or "My laptop screen is cracked, please open a ticket." Or with curl:

```bash
curl -X POST http://localhost:5080/assist -H "X-Demo-User: nurse" -H "Content-Type: application/json" -d '{"message":"Is Ozempic on the formulary?"}'
curl -X POST http://localhost:5080/assist -H "X-Demo-User: nurse" -H "Content-Type: application/json" -d '{"message":"My laptop screen is cracked. Please open a ticket."}'
curl -X POST http://localhost:5080/actions/<id>/approve -H "X-Demo-User: nurse"   # 404 for any other user, and the second time
```

The offline provider (`AI:Provider=Offline`) picks tools with a few keyword rules, so all of this also runs with no model.

## Vetting an MCP server

```bash
dotnet run --project tools/PriorAuthBot.McpVet -- dotnet samples/mcp/DeductibleDynamics.Formulary/bin/Debug/net10.0/DeductibleDynamics.Formulary.dll
```

It prints the server's name and version, each tool's description and schema, any lint findings, and an `Mcp:Servers` entry with each tool's SHA-256 fingerprint. Read the descriptions, decide which tools are read-only, and commit the entry. At startup PriorAuthBot drops a server whose name or version differs, and a tool that is not listed, whose fingerprint changed, or whose description trips the lint. Tool names are prefixed with the server name, and every result is marked as external data and cut to 4,000 characters. In production, pin the server's package too, for example `"Command": "dnx", "Arguments": ["DeductibleDynamics.Formulary@1.0.0", "--yes"]`.

## PriorAuthBot as an MCP server

`/mcp` (Streamable HTTP, stateless) has one tool, `search_policies`. Connect an MCP client to it with a token for PriorAuthBot (Entra) or, in Development, the `X-Demo-User` header. With Entra sign-in, `/.well-known/oauth-protected-resource` tells the client the authorization server and the scope (`Mcp:Server`).

## Configuration

| Setting | Meaning |
|---|---|
| `Tools:Hr:BaseAddress`, `Tools:Hr:Scopes` | The HR API and the delegated scope PriorAuthBot asks for (`api://dd-hr/Pto.Read`) |
| `Tools:Downstream` | PriorAuthBot's app registration and the managed identity used as its client assertion for on-behalf-of (no secret) |
| `Tools:DevelopmentTokens` | Development only: the key the development token provider and the mock HR API share |
| `Mcp:Servers:<name>` | One allowlisted server: transport, command or URL, expected name and version, and its tools with `Sha256` and `ReadOnly` |
| `Mcp:Server` | The protected resource metadata for `/mcp` |
